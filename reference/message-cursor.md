# 消息游标查询

`GET /api/messages/cursor` 需要 Bearer Token。原 `GET /api/messages?page=1&pageSize=20` 保持不变。

## 参数与顺序

| 参数 | 含义 |
|---|---|
| `limit` | 默认 20，范围 1～100；非法值返回 400，不执行页码接口的裁剪 |
| `before` | 排他边界，获取位置更旧的消息，按接收时间、ID 降序 |
| `after` | 排他边界，获取位置更新的消息，按接收时间、ID 升序 |

不传边界时返回最新消息，按接收时间、ID 降序。同一请求不能同时传 `before` 和 `after`，但两个独立请求可以并行。

支持与消息列表相同的 `query`、`status`、`level`、`webhookConfigId`、`pinned`、`from`、`to` 筛选。时间使用 RFC 3339；`from`、`to` 均包含边界。连续翻页应保持筛选条件不变，切换筛选条件后重新加载。此接口不使用 `page`、`pageSize`。

## 响应

沿用 `code`、`msg`、`data` 包装，`data` 包含：

```json
{
  "items": [],
  "hasMore": false,
  "nextCursor": null,
  "startCursor": null,
  "endCursor": null
}
```

- `items`：与旧列表相同的消息预览，包含 `summary`，不包含完整正文。
- `hasMore`：沿当前查询方向是否还有下一批；通过多读取一条判断，不统计 `total`。
- `nextCursor`：还有下一批时等于 `endCursor`，用于沿当前方向继续查询，否则为 `null`。
- `startCursor`、`endCursor`：本批第一条、最后一条消息的位置；空结果时均为 `null`。

游标为 URL 安全的不透明字符串，包含版本、完整精度的接收时间和 UUID。客户端原样传回，不应解析或自行构造。它不是身份凭证，所有请求仍执行归属和软删除检查。非法、空、过长或未知版本的游标返回 400。

游标无需新增数据库字段，也不依赖对应消息仍存在；边界消息删除后仍可继续查询。

## 客户端使用

1. 首次请求 `/api/messages/cursor?limit=20`，返回最新消息，降序排列。保存 `startCursor` 作为最新位置，保存 `endCursor` 作为最旧位置。
2. 加载历史时传 `before=<最旧位置>`，将返回数据追加到列表底部，使用返回的 `endCursor` 更新最旧位置。
3. 收到 SSE `message.created` 时，传 `after=<已保存的最新位置>`。返回数据升序排列，按 ID 去重合并后自行按列表顺序展示。
4. 若新增查询的 `hasMore=true`，传 `after=<nextCursor>` 继续查询；每批用非空 `endCursor` 更新最新位置。历史查询则以 `before=<nextCursor>` 继续。
5. 空结果不覆盖之前保存的位置。首次加载为空、没有游标时，收到通知后重新执行无边界查询。

不要直接用 SSE 的最新消息位置作为 `after` 起点，否则会跳过该消息及之前尚未读取的消息。短时间内多个通知应合并刷新；拉取过程中再次收到通知时应安排后续查询，避免忽略变化。

## 一致性边界

这是接收顺序分页，不是可靠同步日志或固定快照：

- 已读、置顶、删除等更新不会通过增量查询同步；筛选匹配关系也可能变化。
- 新写入、软删除与状态变化可能发生在两次请求之间。
- 接收时间不是事务提交序号。晚提交消息或系统时钟回拨可能产生位于旧游标之前的消息，因此不能保证仅靠 `after` 完成无遗漏同步。
- SSE 为尽力而为，不提供重放。重连、回到前台时仍应刷新最新列表并按需同步未读数。

## 索引与升级

Server 启动时通过新增迁移自动创建索引；Workers 按现有部署流程应用 D1 迁移。迁移不新增业务列、不清理数据，创建索引的耗时取决于现有消息量。

两端新增未删除消息的 `(created_at, id)` 和 `(webhook_config_id, created_at, id)` 部分索引，支持双向定位。其他筛选可能增加扫描量，正文 `LIKE '%关键词%'` 搜索不因此获得全文索引能力。
